# Omni 新用户激活与召回方案

**状态**：已确认
**确认日期**：2026-07-28
**目标分支**：`dev/omni`

## 1. 决策结论

Omni 采用“信任承接 + 首次激活 + 分层召回”的组合方案。

- Omni 公开首页负责所有新访客点击后的信任、注册、首次成功和充值转化。
- 方案上线后长期保持开启；会过期的是每个用户的一天体验订阅，不是活动本身。
- 新用户完成邮箱验证后获得 `$1`、24 小时有效的新人体验订阅。
- 新人体验过期后仍为零成功请求的用户，可在注册后 7 天内回来领取一次 `$2`、24 小时有效的召回体验订阅。
- 第二笔额度不自动发放，必须由用户主动回来领取。
- 微信 `welsir02` 作为人工配置支持入口，不作为领取免费额度的前置条件。
- 已充值但仍为零成功请求的用户不再追加免费额度，直接进入最高优先级人工支持。

## 2. 业务目标

本方案要同时完成四件事：

1. 让进入公开首页的新访客快速理解 Omni 的可信度、使用方式和试用条件。
2. 让完成注册的用户尽快产生第一次成功 API 请求。
3. 区分不会配置、尝试失败、已经成功和付费后仍失败的用户。
4. 用有限的赠送额度召回仍有真实意愿的人，避免一次性向所有账号发放 `$3`。

## 3. 统一口径

### 3.1 额度与支付

- 用户使用人民币支付。
- 充值兑换比例为 `¥1 = $1 API 计算额度`。
- API 输入、输出和缓存按照模型美元价格计算。
- 用户实际扣费为模型美元成本乘适用分组倍率。
- Pro 自营号池当前对用户按 `0.2x` 扣费。
- 试用额度不可提现，付费额度永久有效。

### 3.2 成功使用

“已经使用”只认定为：

> 至少产生一次成功完成并正常计费的 API 请求。

以下行为均不算成功使用：

- 登录；
- 打开控制台或文档；
- 创建 API Key；
- 发起失败请求；
- 仅完成充值。

## 4. 完整用户旅程

### 阶段一：公开首页信任承接

未登录新访客访问 Omni 根地址时直接进入信任承接页，而不是充值页或登录页。

承接页需要让用户立即知道：

- 完成邮箱验证后会自动获得免费体验额度；
- 无需先充值即可验证服务；
- 支持多种支付渠道；
- 使用不满意可按实际使用比例退款；
- 付费额度永久有效；
- 遇到配置问题可以通过微信 `welsir02` 获得人工支持。

公开承接页不展示体验额度金额、计价倍率或最低充值金额。具体权益和到期时间在用户注册并登录后的激活页展示，内部计费口径仍按本方案第 2 节执行。

主操作面向新用户注册，已有账户登录为次操作。

### 阶段二：注册与验证

- 注册必须完成邮箱验证。
- 邮箱验证和注册可用性仍由站点原有注册设置负责，激活活动不得额外拦截或关闭注册。
- 优先允许 Gmail、QQ、Foxmail、163、126、Outlook、Hotmail、iCloud 等常用邮箱。
- 企业邮箱可以通过有效 MX 记录等方式判断。
- 未完成邮箱验证的账号不获得新人体验订阅。
- 邮箱验证完成后自动进入首次调用流程，而不是停留在通用 Dashboard。

### 阶段三：新人体验

邮箱验证成功后，用户获得：

- `$1` API 计算额度；
- 24 小时有效期；
- 面向 Pro 自营号池的体验资格。

这一阶段的目标不是提供长期免费使用，而是帮助用户证明：

- API Key 可用；
- 客户端配置正确；
- 模型可以成功响应；
- Omni 能够解决其实际调用需求。

### 阶段四：首次调用

`/activation` 本身承担首次调用引导，不把新用户带到通用 Key 管理页学习内部分组概念。

页面按顺序呈现三个步骤：

1. `体验额度已到账`：邮箱验证后由系统自动完成。
2. `创建体验 Key`：用户只执行一次创建操作，系统自动绑定当前体验资格，不展示分组选择。
3. `完成首次调用`：Key 就绪后直接展示可复制的 `curl`，调用公共 `/v1/responses` 端点并产生真实模型响应。

首次调用区域同时提供：

- 复用应用顶部的页面标题，正文不重复渲染相同标题和说明；
- 有效期直接展示服务端 `active_group.expires_at`，并说明到期后自动失效；
- `macOS / Linux` 与 `Windows` 两种命令；
- 根据所选系统说明如何打开 Terminal 或 PowerShell、粘贴命令、按回车以及看到什么响应算成功；
- 单一“复制命令”操作，不依赖 `jq`、安装脚本或额外工具；
- “刷新调用状态”，由服务端成功请求事实确认是否完成，前端不伪造成功；
- “配置 Codex”作为次操作，打开现有配置弹窗；其他客户端仍可在弹窗内选择。

页面内分步引导是主路径。本阶段不增加自动弹出的 JS 漫游；如后续数据仍表明用户找不到下一步，再单独评估用户主动触发的帮助引导。

系统持续判断是否产生成功 API 请求：

- 成功：立即停止激活类邮件，进入试用后充值转化。
- 未成功：按照用户行为进入分层回访。

### 阶段五：零成功请求分层

#### A. 只注册，未尝试

识别特征：

- 已完成注册和邮箱验证；
- 没有成功请求；
- 没有创建 Key 或没有发起调用。

处理目标：

- 告诉用户下一步是什么；
- 降低开始使用的理解成本；
- 暴露微信人工配置支持。

#### B. 已尝试，但没有成功

识别特征：

- 已创建 Key 或存在失败请求；
- 成功请求数仍为零。

处理目标：

- 帮助定位客户端、Base URL、模型、Key 或请求格式问题；
- 根据失败类型提供有针对性的帮助；
- 暴露微信人工配置支持。

#### C. 已充值，但没有成功

识别特征：

- 存在成功充值；
- 成功请求数仍为零。

处理目标：

- 作为最高优先级服务问题处理；
- 由人工主动介入；
- 不再追加免费额度，以免掩盖真实的配置或产品问题。

#### D. 已产生成功请求

处理方式：

- 停止所有激活和召回邮件；
- 根据试用剩余情况引导继续使用；
- 在体验价值已经成立后再引导充值。

### 阶段六：沉默召回

满足以下条件的用户进入召回：

- 新人体验订阅已经过期；
- 成功请求数仍为零；
- 没有领取过召回体验；
- 未进入“已充值但零成功”的人工支持分支。

召回规则：

- 注册后 7 天内可回来领取一次；
- 领取后获得 `$2`、24 小时有效的召回体验订阅；
- 与新人体验不叠加；
- 每个用户最多领取一次；
- 用户必须主动回来领取，不自动入账。

召回后：

- 产生成功请求：停止召回，进入正常充值转化。
- 仍未产生成功请求：停止继续补贴，邀请进行人工访谈或配置排查。

### 阶段七：充值与正常使用

首次成功请求后再进行充值引导：

- 最低支付金额为 `¥10`；
- 支付 `¥10` 入账 `$10 API 计算额度`；
- 付费额度永久有效；
- 后续按照模型美元成本和用户所选分组倍率扣费。

## 5. 邮件原则

- 邮件以自助解决为主，微信人工支持为兜底。
- 不以“加微信领钱”作为主要诱因。
- 不向已经成功调用的用户继续发送激活邮件。
- 不向已充值但零成功请求的用户继续堆叠免费额度。
- 同一阶段避免高频重复触达。
- 邮件内容必须对应用户真实状态，不能只按“是否注册”粗分。

## 6. 方案选择与放弃项

### 已选择：分阶段 `$1 + $2`

第一笔用于验证产品，第二笔用于验证用户是否仍有真实意愿。只有主动回来的沉默用户才获得第二笔额度。

### 未选择：注册一次性发放 `$3`

原因：

- `0.2x` 下 `$3` 可覆盖较多模型原价用量；
- 无法区分真实用户和仅领取赠送额度的账号；
- 对没有开始使用的人继续增加余额，不能解决配置或信任问题。

### 未选择：完全依赖人工回访

原因：

- 初始规模可行，但无法稳定覆盖增长后的注册量；
- 适合作为高价值用户和异常分支的兜底，不适合作为主流程。

## 7. 核心指标

主漏斗：

1. 公开首页访问到注册；
2. 注册到邮箱验证；
3. 邮箱验证到 24 小时内首次成功请求；
4. 首次成功请求到首次充值；
5. 首次充值到 7 日继续使用。

召回漏斗：

1. 新人体验过期且零成功请求人数；
2. 召回邮件触达人数；
3. `$2` 召回体验领取率；
4. 召回后首次成功请求率；
5. 召回后首次充值率。

服务风险指标：

- 已充值但零成功请求人数；
- 失败请求的主要错误类型；
- 人工支持介入量和解决率；
- 同邮箱、设备或网络环境的异常注册与领取行为。

## 8. 成功标准

方案是否有效，不以注册数或赠送额度领取数单独判断，而以以下结果判断：

- 邮箱验证后 24 小时首次成功请求率上升；
- 已充值但零成功请求人数下降；
- 召回用户产生首次成功请求，而不是只领取额度；
- 首次成功请求能够继续转化为充值和 7 日使用；
- 平均赠送额度低于一次性向所有用户发放 `$3`。

## 9. 本阶段不包含

本设计只确定业务方案，不确定以下实现：

- 订阅套餐、分组和额度字段如何配置；
- 邮件服务、队列和定时任务如何实现；
- 埋点事件、数据表和报表结构；
- Umami、UTM 和渠道来源归因；
- 防刷规则的具体阈值；
- 生产发布和数据迁移步骤。

这些内容必须在本方案确认后，由独立实施计划继续拆解。
