# Text-Only Moderation With Attachment Pass-Through Design

## Goal

Preserve normal Omni image and file workflows while protecting configured OAI
accounts with complete-context MiniMax text moderation before downstream account
selection.

## Approved Boundary

- Sub2API audits all visible request-side text: system, developer, user,
  assistant, tool calls, tool results, instructions, image prompts, and file
  captions.
- Image pixels and file bytes are not decoded, fetched, OCRed, extracted, or sent
  to MiniMax in the first release.
- Safe attachment metadata is limited to media kind, normalized MIME type,
  source class, and a normalized extension when available. Raw URLs or URIs,
  opaque file IDs, file names, Base64 bodies, signed URL queries, file contents,
  headers, cookies, and provider credentials must never enter the moderation
  transcript. `source=file_id` records only the reference class, never the ID.
- A strict `block` or `review` text verdict rejects the complete client request,
  regardless of whether it contains attachments.
- A strict `allow` text verdict permits the original request and its attachments
  to continue unchanged to the normal downstream path.
- The mere presence of an attachment is not an error and must not cause a local
  block, moderation 503, or automatic unsafe verdict.

## Request Flow

1. Parse the supported OpenAI Responses, OpenAI Chat, Anthropic Messages,
   Gemini, OpenAI Images, and Grok media request shapes before account selection.
2. Build the existing stable role-tagged full-context transcript from text,
   tool traffic, and safe attachment markers.
3. Keep attachment bytes and remote resources outside the moderation request.
4. Split and cache the normalized text transcript using the existing versioned
   incremental moderation path.
5. Send only uncached text chunks to the OpenAI-shaped adapter and MiniMax.
6. Permit downstream account selection only after every chunk returns a strict
   allow decision.

The adapter remains a text-classification boundary. Structured media must not be
generated by the Sub2API runtime moderation client. A direct structured-image
call returns a deterministic flagged local-policy result without invoking
MiniMax. This is defense in depth for a protocol violation, not the normal
Sub2API attachment path and not evidence of image-pixel moderation.

## Supported Attachment Metadata

The extractor may emit bounded markers such as:

```text
[attachment kind=image mime=image/png source=inline]
[attachment kind=file mime=application/pdf source=file_id extension=.pdf]
```

Markers use a canonical ordered grammar with `kind`, optional normalized `mime`,
optional `source`, and optional normalized `extension`. They must be
deterministic and must not include:

- image or document bytes;
- Base64 payloads;
- raw signed URLs or URL query strings;
- raw URLs or URIs;
- opaque file IDs or file names;
- headers, cookies, or credentials;
- arbitrary metadata objects;
- content fetched from a URL or file ID.

If a protocol exposes only an opaque `file_id`, the marker may record
`source=file_id` without copying or resolving the value. A valid marker is
neutral uninspected metadata; attachment presence alone is neither an allow nor
a block/review reason, and visible surrounding text remains fully auditable.

## Protocol Boundary

- OpenAI Chat projects ordered roles, tool/function calls and results, and
  `image_url` or file parts.
- OpenAI Responses projects `instructions`, ordered input items, tool calls and
  outputs, `input_image`, and `input_file`, including accumulated WebSocket
  request context.
- Anthropic projects system/messages, `tool_use`/`tool_result`, image, and
  document blocks.
- Gemini projects system instructions, content roles,
  `functionCall`/`functionResponse`, `inlineData`, and `fileData` in either
  supported casing.
- OpenAI Images and Grok media build a separate moderation body from the parsed
  prompt plus safe reference/upload markers; their original media request body
  remains unchanged for downstream forwarding after allow.

## Classifier And Cache Revision Contract

The adapter exposes the active classifier policy revision on `/readyz` and every
successful Moderations response. Sub2API pins the expected revision, verifies
`/readyz` before the first cache read for each base-URL/revision pair, and checks
each uncached result before writing its verdict. A response mismatch invalidates
the remembered readiness check. The text
projection revision `incremental-full-context-v2-attachment-text-only` and
classifier policy revision `minimax-strict-policy-v5` both participate in chunk
hashes and Redis namespaces so verdicts from the old structured-image policy or
an older classifier prompt cannot be reused.

## Error Handling

- Text moderation keeps the existing three-total-attempt transient retry and
  fail-closed behavior.
- Unsupported or malformed request JSON remains a request-validation failure.
- A valid request containing a valid attachment is not a moderation-service
  failure.
- MiniMax prompt injection, malformed decisions, uncertainty, `review`, and
  sensitive-provider results remain blocked.
- No moderation failure path falls back to OAI.

## Explicit Residual Risk

A request whose visible text is benign but whose image pixels or file content
contains harmful instructions can pass text-only moderation and reach OAI. The
first release accepts this risk to preserve normal attachment use. Tool-extracted
text becomes auditable in a later request only if that text is present in the
next outbound context; this does not retroactively protect the first attachment
request.

OCR, PDF/document extraction, archive inspection, malware analysis, and a
multimodal moderation model are separate future capabilities. This release must
not claim that they are covered.

## Verification

- Normal text plus image, PDF, code file, archive, or opaque file ID reaches the
  mocked downstream path after a strict text allow.
- Dangerous text plus any attachment blocks before account selection and before
  OAI network traffic.
- Attachment-only requests produce bounded metadata markers and do not fail just
  because a media part exists.
- MiniMax moderation payloads contain no image parts, Base64 data, raw attachment
  bytes, signed URL queries, or resolved file contents.
- Responses `input_image` and `input_file`, Chat `image_url`, Anthropic `image`
  and `document`, Gemini `inlineData` and `fileData`, OpenAI Images and Grok media
  prompts/uploads, tool traffic, and `Continue` after dangerous history receive
  protocol-level tests.
- Missing or mismatched readiness/response classifier revisions fail closed
  without reading or writing incompatible cached verdicts.
- A synthetic image-only prompt-injection case is documented as an expected
  text-only false negative, while the same injected text exposed through a tool
  result blocks the next request.
- Existing long-context, incremental-cache, transient-retry, fail-closed, gzip,
  WebSocket, and no-account-selection assertions remain green.

## Non-Goals

- Inspecting image pixels or file contents.
- Fetching attachment URLs or resolving provider file IDs.
- Blocking all attachments.
- Deploying, changing production configuration, or claiming production safety
  before a real MiniMax classification and the complete local acceptance suite.
