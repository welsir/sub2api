# 虎皮椒微信支付原生接入设计

## 背景

Omni V2 当前通过支付服务商实例统一管理支付创建、订单查询、异步通知、退款和用户余额入账。支付宝已使用 ZPay 的易支付协议；虎皮椒微信渠道使用独立协议，无法直接复用易支付适配器。

本次只在 `dev/omni` 产品线增加虎皮椒微信扫码充值，不同步到 `main`、公司分支或团队分支。

## 目标与非目标

目标：

- 新增一等支付服务商 `xunhupay`，仅声明支持 `wxpay`。
- 支持创建微信扫码订单并在现有二维码界面展示。
- 支持异步通知验签、商户身份校验、金额校验和幂等充值。
- 支持主动查询订单，作为通知丢失时的恢复手段。
- 在管理后台新增虎皮椒配置，并允许将微信支付来源明确选择为虎皮椒。

非目标：

- 首发不支持退款，也不允许管理员为虎皮椒开启退款。
- 不接入虎皮椒支付宝渠道。
- 不引入额外的易支付中转服务。
- 不直接依赖第三方 Go 示例包；只按官方协议实现必要能力。
- 本轮不部署到 43，也不调用真实支付接口；部署和小额实付需要单独授权及商户凭证。

## 方案选择

采用 V2 原生 Provider 方案。虎皮椒作为 `payment.Provider` 的独立实现接入现有 Registry、服务商实例、订单状态机和履约流程。

不直接依赖官方页面链接的 Go 示例。该示例只封装基础签名和请求，没有覆盖生产所需的上下文超时、HTTP 状态、响应验签、通知验签、商户隔离和订单幂等。把协议适配留在仓库内，更容易测试和维护。

## 后端设计

### Provider 能力

新增 `payment.TypeXunhuPay = "xunhupay"` 和 `provider.XunhuPay`：

- `ProviderKey()` 返回 `xunhupay`。
- `SupportedTypes()` 只返回 `wxpay`。
- `CreatePayment()` 调用虎皮椒支付创建接口，将 `url_qrcode` 映射到现有 `QRCode` 字段；移动端可保留 `url` 作为 `PayURL`。
- `QueryOrder()` 使用商户订单号查询并映射为统一的 pending、paid、failed、refunded 状态。
- `VerifyNotification()` 解析表单通知，按官方算法排除 `hash` 与空值后排序签名，使用常量时间比较验签，并校验回调 `appid` 与当前实例一致。只有 `OD` 映射为支付成功。
- `Refund()` 明确返回不支持错误。

配置字段为：

- `appId`：虎皮椒 APPID。
- `appSecret`：虎皮椒 APPSECRET，敏感字段。
- `apiBase`：默认 `https://api.xunhupay.com`，保留备用地址和本地测试服务器的可配置性。
- `notifyUrl`：默认由管理后台按站点域名生成 `/api/v1/payment/webhook/xunhupay`。
- `returnUrl`：默认由管理后台生成 `/payment/result`。

HTTP 请求必须带上下文和固定超时，限制响应体大小，检查非 2xx 状态，并验证成功响应的 `hash`。签名函数不修改调用方传入的数据。

### 回调和履约

新增 `POST /api/v1/payment/webhook/xunhupay`，沿用通用支付通知处理器：

1. 根据回调路径和订单所记录的服务商实例解析正确的虎皮椒 Provider。
2. Provider 完成协议解析、签名与 APPID 校验。
3. 通用支付服务核对订单号、支付金额和预期 Provider。
4. 现有事务与订单状态机完成一次性充值。
5. 成功或已经处理过的合法通知返回虎皮椒要求的 `success`。

重复回调依赖现有订单履约幂等，不新增独立入账逻辑。金额仍由服务层与订单保存金额核对，Provider 只负责可靠解析上游金额。

## 管理端与用户端设计

- 管理后台服务商类型增加“虎皮椒”。
- 虎皮椒只提供微信支付类型，不显示支付宝或自定义方式。
- 配置表单显示 APPID、APPSECRET、API 基础地址、异步通知地址和同步返回地址。
- 虎皮椒不显示退款开关；后端也拒绝把该实例配置为支持退款。
- 微信支付来源选项新增 `xunhupay_wxpay`，显示为“虎皮椒微信支付”。
- 用户发起微信充值时仍使用现有 `wxpay` 方法，不暴露新的用户侧支付类型；路由层根据配置选择虎皮椒实例。
- 支付宝继续选择 `easypay_alipay`，因此 ZPay 和虎皮椒不会相互抢单。

## 错误处理与安全边界

- 缺少 APPID、APPSECRET 或回调地址时拒绝创建服务商实例。
- 创建或查询接口超时、非 2xx、无效 JSON、错误码、签名不一致均返回明确错误，不创建已支付事实。
- 回调签名错误、APPID 不一致、金额异常或未知订单不得入账。
- 不对通知时间戳做过短窗口拦截，以免虎皮椒重试通知被误拒；重放风险由签名、商户隔离、订单金额和履约幂等共同控制。
- 日志和 API 响应不得暴露 APPSECRET 或完整签名原文。

## 测试与验收

后端测试覆盖：

- 配置校验和 Provider 工厂注册。
- 官方签名规则、空值排除和签名常量时间校验。
- 创建支付请求字段及二维码响应映射。
- 创建响应错误码、HTTP 错误和响应签名错误。
- 查询状态映射。
- 合法 `OD` 通知、伪造签名、错误 APPID、非支付状态和扩展字段。
- 重复通知不重复充值、金额不一致拒绝入账、Provider 不匹配拒绝入账。
- 虎皮椒退款明确不支持。

前端测试覆盖：

- 服务商类型、配置字段、回调路径和支持类型。
- 微信来源新增虎皮椒并能稳定保存、读取和归一化。
- 虎皮椒配置不展示退款能力。

本地完成条件：目标 Go 测试、相关支付服务测试、前端目标测试、后端构建/静态检查和前端类型检查通过，最终差异只包含本功能及其设计/计划文档。
