# 43 V2 单跳稳定代理池设计

**日期：** 2026-07-22
**目标分支：** `dev/omni`
**状态：** 已确认，采用方案 A
**边界：** 本文冻结设计，不代表已经开发或部署

## 1. 结论

43 服务器 V2 不再追求固定出口 IP，也不建设 IPReed 或其他双跳。最终方案是：

- 一个 Mihomo 实例承载 WgetCloud 全部真实候选节点；
- 五条独立生产 Lane，每条 Lane 同时只选择一个单跳节点；
- Sub2API OAuth 账号只绑定 Lane 对应的代理 ID，账号 `proxy_id` 是出口唯一事实；
- V2 部署目录运行独立稳定池控制器，负责探测、评分、晋升、摘除、账号亲和和回滚；
- 29 个真实节点参加竞争，套餐日期、重置日期等 3 个伪节点自动排除；
- 生产最多使用 5 个节点，未经验证的节点不能接触线上流量；
- 上线前观察 2 小时，不采用 24 小时观察期。

这是一套“稳定优先、延迟受控”的单跳系统，不是永远追逐最低延迟的测速器。

## 2. 关键取舍

### 2.1 不做双跳

双跳增加连接、TLS、带宽和供应商故障面。固定出口 IP 不是当前硬需求，因此没有必要用更复杂的链路换取不确定的稳定性。

### 2.2 单 Mihomo、五条 Lane

43 是资源紧张的 2 GiB 主机。一个 Mihomo 进程比五个独立代理容器更节省内存，也更容易统一加载订阅和切换节点。Lane 仍是独立监听器与独立策略组，所以一个节点故障只影响绑定该 Lane 的账号。

### 2.3 Sub2API 是出口事实来源

V2 应用容器不再设置 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 等全局代理环境变量：

```text
OAuth account -> Sub2API proxy ID -> Mihomo Lane listener -> WgetCloud node
```

后台可以直接解释真实出口，不再依赖容器外部黑盒代理。

## 3. 运行架构

### 3.1 组件

1. `sub2api-v2-app`
   - 处理用户请求并读取账号 `proxy_id`；
   - 不配置全局代理环境变量。

2. `sub2api-v2-mihomo`
   - 加载 WgetCloud 订阅；
   - 提供 5 个生产 Lane 监听器；
   - 提供 3 个候选并发探测监听器与 1 个 Canary 监听器；
   - 控制端口仅允许 Docker 内网访问，不开放公网。

3. `sub2api-v2-proxy-controller`
   - 是独立网络控制器，不链接或修改 Sub2API 核心代码；
   - 通过 V2 管理 API 列出账号、更新 `proxy_id` 和触发账号 SSE 测试；
   - 状态与审计写入 `/data/sub2api-v2/proxy-pool/`；
   - 只允许 Docker 内网或本机访问管理端口。

4. Sub2API V2
   - 继续使用现有 `accounts.proxy_id` 保存账号真实出口绑定；
   - 不增加稳定池表、后台服务或业务代码。

### 3.2 Lane 与代理记录

| Lane | Sub2API 代理名 | Mihomo 地址 |
| --- | --- | --- |
| Lane 1 | `v2-stable-lane-1` | `mihomo:19081` |
| Lane 2 | `v2-stable-lane-2` | `mihomo:19082` |
| Lane 3 | `v2-stable-lane-3` | `mihomo:19083` |
| Lane 4 | `v2-stable-lane-4` | `mihomo:19084` |
| Lane 5 | `v2-stable-lane-5` | `mihomo:19085` |

代理 ID 不写死在代码中，由控制器按受管代理名解析并保存。V2 当前代理 ID `6` 保留为全局回滚目标，不改名、不删除。

### 3.3 账号亲和

控制器只处理当前存在、平台为 OpenAI、类型为 OAuth、状态有效的账号：

- 新增账号自动进入一致性分配；
- 删除、停用或不可用账号自动离开；
- Lane 集合不变时，同一账号保持同一出口；
- Lane 故障时只重算该 Lane 的账号；
- 只有一个账号时绑定当前最佳合格 Lane；
- 没有账号时继续网络观察，但不做需要账号证据的晋升或摘除。

一致性分配使用 Rendezvous Hash，键是稳定账号 ID，候选是当前健康 Lane；Lane 当前账号数只作为轻量平衡项，避免拥挤但不为了绝对均匀频繁搬迁。

## 4. 节点发现与过滤

控制器从 Mihomo provider API 读取订阅节点，不在 Sub2API 数据库复制供应商凭据或节点明文配置。节点进入候选池前必须：

- 是 provider 返回的可拨号代理；
- 名称不匹配套餐日期、剩余流量、重置日期、官网提示等伪节点规则；
- 具有稳定的 provider/name 标识；
- 不在隔离期。

订阅变化按标识合并：新节点从未验证状态开始，消失节点退出候选；生产节点消失按明确故障处理。

## 5. 探测策略

### 5.1 周期与覆盖

每 2 分钟一轮：

- 并发检查所有正在承载账号的生产 Lane；
- 并发检查 3 个非生产候选；
- 29 个候选约 20 分钟轮完；
- 2 小时观察期约有 6 个完整候选轮次。

调度带抖动和全局并发上限；上一轮未结束时不堆积下一轮。

### 5.2 动态 OAuth 探针

探针固定使用 `gpt-5.4-mini`，发送最小流式 `hi`。只有 HTTP 200、合法 SSE、有效完成事件同时满足才成功，并记录首包与完整时延。

探针账号从 V2 管理 API 动态选择，不设置专用账号：

- 2 个或更多合格账号：失败必须由两个不同账号复核；
- 只有 1 个账号：新连接重试，并增加匿名 OpenAI 传输探针；
- 没有账号：只做 TCP、TLS 和匿名 HTTP 探针，标记“证据不足”。

候选节点在进入 Canary 前不修改任何账号绑定。由于现有账号测试接口不支持临时覆盖代理，只有 Canary 阶段才允许控制器对一个 V2 账号执行“记录旧代理、切到 Canary、测试、失败立即恢复”的显式迁移。

### 5.3 账号错误与节点错误分离

OAuth 401、403、429、账号过期、额度不足或不可调度，不扣节点稳定分。匿名请求返回 401 代表网络和 TLS 可达；连接超时、TLS 错误、EOF、502/503 或没有有效 HTTP 响应才是传输失败证据。

## 6. 稳定门槛与评分

节点进入生产稳定池必须满足：

- 最近有效样本成功率不低于 99%；
- 连续成功至少 3 次；
- P95 不高于 2.5 秒；
- 不在隔离或手动禁用状态。

`P95 > 5 秒` 记为明显退化。排名顺序固定为：稳定门槛、成功率、连续成功次数、P95，最后才比较平均延迟。

性能替换必须同时满足：

- 候选稳定性不低于当前节点；
- 候选 P95 至少快 20%；
- 当前节点连续 3 个统计窗口超过 2.5 秒；
- 30 分钟内没有发生普通性能替换。

“30 分钟最多替换一个”只限制慢但仍可用的性能优化，避免小幅波动造成来回切换。明确故障不等待这 30 分钟。

## 7. 故障、Canary 与回滚

### 7.1 明确故障

生产 Lane 连续失败 2 次并完成相应账号复核后：

1. 立即摘除该节点；
2. 只处理该 Lane 的账号；
3. 从已验证稳定池选择替代节点；
4. 更新 Mihomo Lane 选择器并回读；
5. 通过动态 OAuth 探针验证；
6. 失败则恢复旧选择器，或把受影响账号回滚到代理 ID `6`；
7. 故障节点隔离 30 分钟后才重新参加候选探测。

没有合格替代节点时，不得把未验证节点推入生产；受影响账号回滚到代理 ID `6`。

### 7.2 Canary

候选首次晋升前，先在只承载探针流量的 Canary Lane 使用一个动态 OAuth 账号观察 30 分钟。Canary 不接普通用户调度，不计入 5 条生产 Lane；失败立即恢复，不改变线上账号绑定。

### 7.3 全局保护

以下情况停止自动执行并逐账号回滚到代理 ID `6`：

- Mihomo 控制器和生产监听器同时不可用；
- Lane 配置与数据库状态无法对账；
- 自动切换后多个 Lane 同时传输失败；
- 控制器无法确认写入是否成功。

每个账号记录旧代理、目标代理和验证结果；失败立即恢复该账号旧值。

## 8. 后台管理

独立控制器的内部管理 API 和 CLI 至少提供：

- 查看全部真实节点健康状态；
- 查看 Top 5 与每条 Lane 的实际节点；
- 查看账号到 Lane 的分配；
- 固定和解除固定 Lane；
- 手动测试节点；
- 切换 `observe` 与 `auto`；
- 查看切换、回滚和账号迁移审计。

手动固定只阻止普通性能替换；确认故障时仍自动撤离。状态接口必须展示 Mihomo 实际状态与控制器期望状态，不能只显示期望配置。首期不把该能力嵌入 Sub2API 前端。

## 9. 上线顺序

1. 保持代理 ID `6` 不变；
2. 部署 Mihomo、5 条生产 Lane 和探测 Lane，但不绑定账号；
3. 控制器以 `observe` 模式运行 2 小时；
4. 验证候选覆盖、伪节点过滤、探针分类和 Top 5；
5. 动态选择一个 OAuth 账号灰度 30 分钟；
6. 账号逐个迁移，每次迁移后验证，失败立即恢复；
7. 全部稳定后开启 `auto`；
8. 删除 V2 应用容器中多余的全局代理环境变量，保留代理 ID `6` 回滚。

## 10. 非目标

- 不建设双跳或固定出口 IP；
- 不修改 Sub2API 后端、前端、Ent schema 或数据库迁移；
- 不复用 39 上命名为“两跳”但实际为单跳的黑盒结构；
- 不让所有账号共享最低延迟节点；
- 不因账号 401、403、429判定节点故障；
- 不在证据不足时自动晋升或摘除；
- 本设计提交不修改代码、不操作 43 生产环境。
