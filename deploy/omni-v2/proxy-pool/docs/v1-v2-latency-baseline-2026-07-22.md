# 43 服务器 V1 / V2 延迟基线（2026-07-22）

## 结论边界

本记录是新稳定池切流前的基线，不代表新 V2 单跳稳定池的最终收益。

- V1 共同账号 `72 / 78 / 79` 当前使用代理 ID `5`。
- V2 共同账号 `72 / 78 / 79` 当前使用回滚代理 ID `6`。
- V2 稳定池仍为 `observe`，尚未执行 Lane 切换、Canary 或账号迁移。
- 因此，本轮回答的是“V1 原路径与 V2 原路径的真实流量表现”，Canary 后必须按相同 SQL 口径复测。

## 统计口径

- 数据源：V1、V2 各自 PostgreSQL `usage_logs`。
- 时间窗：采样时点向前 24 小时。
- 账号：仅共同的 OpenAI OAuth 账号 `72 / 78 / 79`。
- 模型：共同样本最多的 `gpt-5.6-sol`。
- 请求：`stream=true`、`input_tokens>0`、`duration_ms>0`。
- 上下文分桶：`<=1K`、`1K-4K`、`4K-16K`、`16K-64K`、`>64K` 输入 Token。
- 主指标：首 Token 延迟（TTFT）。总耗时受输出 Token 数影响，只作辅助参考。
- 变化率：`(V2 / V1 - 1) × 100%`，负数表示 V2 更快。

## 初步判断

1. V2 当前原路径的尾延迟优于 V1：整体 P95 TTFT 低约 14.9%，`1K-16K` 分桶改善最明显。
2. V2 并非所有分桶都更快：`<=1K`、`16K-64K` 和 `>64K` 的平均或 P50 TTFT 暂时更慢。
3. `16K-64K` 的总耗时差异很大，但双方平均输出长度和请求构成不同，不能直接归因于代理。
4. V1 样本量明显高于 V2，特别是长上下文分桶；应重点看 TTFT、P95 和后续同条件重复结果，而不是只看一次平均值。
5. 新稳定池首轮探测的香港节点收到 OpenAI 403，已被正确记为失败；这些节点不会进入生产稳定池。

## 稳定池探测口径校准（2026-07-22 20:13 CST）

控制器记录的节点 `P95` 不是纯网络延迟。当前一次探测从读取可用账号开始计时，依次包含刷新账号、临时切换代理、执行 `gpt-5.4-mini` 最小 SSE、恢复原代理等完整后台操作。因此此前 `2.5 秒` 的生产门槛无法与该指标口径匹配。

使用无效 Token 请求 OpenAI `/v1/models`，仅测量代理链路、TLS 和 OpenAI 首响应，得到以下只读样本：

| 路径 | 样本结果 | 首响应范围 | 说明 |
|---|---:|---:|---|
| 39 当前 OpenAI 两跳 | 5/5 HTTP 401 | 3.711–5.753 秒 | 规则确认命中 `OpenAI两跳出口` |
| 43 新加坡 02 单跳 | 4/4 HTTP 401 | 0.788–1.712 秒 | 当前 `V2-PROBE-1` |
| 43 新加坡 03 单跳 | 3/4 HTTP 401 | 0.742–0.771 秒 | 另 1 次 TLS EOF，仍需真实 SSE 稳定性约束 |
| 43 日本 01 单跳 | 4/4 HTTP 401 | 0.699–0.744 秒 | 仅说明网络快；真实 SSE 探测不稳定，不能据此入池 |
| 43 AWS 直连 | 3/3 HTTP 403 | 0.032–0.044 秒 | 响应快但上游拒绝，不可承载生产 |

结论：43 单跳链路本身明显快于 39 当前两跳，控制器出现 4.5–10.6 秒主要来自完整账号测试与模型处理，并非代理网络本身耗时。生产资格仍要求成功率至少 99%、连续成功至少 3 次；完整探测 P95 调整为不超过 8 秒，严重慢阈值调整为 12 秒。网络测速不能覆盖真实 SSE 失败，HTTP 401 快速返回也不能替代账号探测。

## Canary 后复测要求

Canary 满 30 分钟后，使用相同账号、模型、时间窗和上下文分桶重复本表，并额外记录：

- Canary Lane 对应节点和出口 IP；
- 请求成功率及 OpenAI 403 / 429 / 5xx 数量；
- TTFT 平均、P50、P95；
- 总耗时平均、P50、P95；
- 每个分桶至少 30 个样本；不足时延长观察，不下确定性结论。

只有 Canary 后的结果，才能判断新 V2 单跳稳定池相对 V1 是否真正改善。
